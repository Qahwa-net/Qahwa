# ADR-059: SQL Server as a second database

**Status:** accepted (L12)

## Context
The data layer was written against `ISqlDialect`, `IDbConnectionFactory` and `ISchemaInspector` so that PostgreSQL would not be the only choice. Many organisations run SQL Server and will not install anything else. The risk of a second database is silent differences: types that lose precision, paging that needs an `ORDER BY`, unique indexes that allow only one empty value, case sensitivity, parameter limits, and tests that only ever ran against one product.

## Decision
- **A new project `Qahwa.Data.SqlServer`** (Microsoft.Data.SqlClient): `SqlServerDialect`, `SqlServerConnectionFactory`, `SqlServerSchemaInspector`, `AddQahwaSqlServer`, `SqlServerSites`. Selected with `Qahwa:Database:Provider` = `Postgres` (default) or `SqlServer`; with several sites (ADR-055) each site chooses its own, so one server can run a PostgreSQL main site and SQL Server sites. SQL Server 2017 or later.
- **Mapping:** text is `nvarchar(140)` / `nvarchar(max)` (any script is stored as typed), numbers `int`, `float`, `decimal(21,9)`, booleans `bit`, `date`, `time(6)`, and moments `datetime2(6)` holding UTC. The inspector reports types with their size (`nvarchar(140)`, `decimal(21,9)`) so a change of size is noticed too.
- **Differences made explicit in the dialect, not scattered:** paging is `OFFSET … FETCH` (every query is ordered); tables, indexes and system tables are created only when missing (`IF OBJECT_ID …`, `IF NOT EXISTS (… sys.indexes …)`); adding a column is `ADD`, dropping an index names its table (`DropIndexSql` and a new `AddColumnSql` on the interface); a **unique index ignores empty values** (`WHERE col IS NOT NULL`) as PostgreSQL does, instead of allowing a single empty one; the series counter is one locked step (`UPDATE … WITH (UPDLOCK, HOLDLOCK)` then insert, in a transaction), so two first uses cannot both insert and numbers stay gapless under concurrency; unique-violation errors 2627, 2601 and 1505 (duplicates found while making a unique index) and duplicate-object errors 2714 and 1913 are recognised; a statement may bind at most 2,000 values (`MaxParameters`), and a longer list of values in a filter is a clear `FormatException` instead of a database error (PostgreSQL's limit is far larger).
- **Parameters keep their meaning:** the driver would send a `DateTime` as the old 3-millisecond `datetime`, which never equals a stored microsecond value and breaks the "changed by someone else" check. `DbCommands` therefore declares `DateTime` as `datetime2`, `DateOnly` as `date` and `TimeOnly` as `time` when the command is a SQL Server one. Every value is still a parameter, never text in the statement; identifiers are quoted with brackets (a closing bracket is doubled) and names inside literals are escaped.
- **The same tests run on both.** The Postgres test classes use a shared fixture; with the environment variable `QAHWA_TEST_DB=sqlserver` the whole data suite runs against a SQL Server container (one container for the whole run; if it cannot start the run fails instead of skipping). Tests that look at catalogs use stack helpers (`TableExistsAsync`, `ColumnCountAsync`, `IndexCountAsync`) so they work on both. `DatabaseBehaviourTests` states the shared promises: unique gapless series under concurrency, many empty values in a unique field but no repeated value, text in any script and case-insensitive search, exact dates, times, money and microsecond moments, conflict detection, hostile text as data, the parameter limit. All 128 data tests pass on PostgreSQL, and 127 on SQL Server (one is about creating PostgreSQL databases). Dialect unit tests check the generated SQL.
- **CLI:** `--provider sqlserver` for `new-site`, `migrate` and `create-admin`; `new-site` creates the database `qahwa_<name>` (name checked and quoted) and writes the site's provider into its file.

## Consequences
- Searches are case-insensitive under SQL Server's usual collation; a database made with a case-sensitive collation would make them case-sensitive. `[ ]` in a search pattern act as wildcards in SQL Server.
- An indexed or unique field of a long-text type cannot be indexed on SQL Server (it can on PostgreSQL); use a short text field for keys.
- Not yet: Azure SQL specifics (works with the same connection string but is untested), always-encrypted columns, SQL Server full-text search, and the whole API suite against SQL Server (the data layer and a real site end to end were run).
