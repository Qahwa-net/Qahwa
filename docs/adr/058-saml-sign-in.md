# ADR-058: SAML 2.0 sign-in

**Status:** accepted (L12)

## Context
Many organisations (ADFS, Shibboleth, older Okta and Entra setups, universities and government bodies) offer SAML 2.0 and not OpenID Connect. SAML responses are signed XML, and XML signatures are a classic source of serious flaws: signature wrapping (an unsigned assertion placed where the code reads, next to a signed harmless one), duplicate ids, weak algorithms, external entities, replay and login CSRF.

## Decision
- **SP-initiated web browser SSO only** (HTTP-Redirect AuthnRequest out, HTTP-POST response back). Unsolicited, IdP-initiated responses are refused: every response must answer a request made here by this browser.
- **Per provider** (`Qahwa:Auth:Saml:Providers:<name>`): `IdpEntityId`, `SsoUrl` (https), one or more signing `Certificates` (base64 or PEM), optional `SpEntityId` (default `<PublicUrl>/api/auth/saml/<name>/metadata`), `EmailAttribute`, `NameAttribute`, `AllowedDomains`, `AutoCreate`, `DefaultRoles`. Settings that cannot work (no certificate, http address, a bad certificate, AutoCreate without domains) stop the server at start with a message.
- **Binding the browser:** the request id, a random relay state and an expiry (10 minutes) are kept in an encrypted, HttpOnly cookie that works once (deleted on every answer). The answer must carry the same relay state and `InResponseTo` that id. The cookie is `SameSite=None; Secure` because the answer is a cross-site POST (in Development over plain http, `Lax`). A response started by someone else (login CSRF) has no cookie and is refused.
- **Signature checks** (`System.Security.Cryptography.Xml`, our own checks around it): RSA with SHA-256, 384 or 512 only (SHA-1 refused); digest SHA-256 or stronger; canonicalisation exclusive or inclusive c14n; the only transforms are enveloped-signature and c14n; exactly one `Reference`, and its `URI` must be `#` plus the id of **the element the signature sits in**; that element is either the Response or the single Assertion that is a direct child of it; at most two signatures; the key is **only** a configured certificate (keys inside the message are ignored); every `ID` in the document must be unique; exactly one Assertion in the whole document; encrypted assertions are refused. The assertion read afterwards is that one signed assertion (or one inside a signed response). A tampered message, a wrapped message, a foreign key and a weak algorithm are all covered by tests.
- **Assertion checks:** issuer equals `IdpEntityId` (response and assertion); Conditions present, `NotBefore`/`NotOnOrAfter` honoured with two minutes of skew; Audience contains this application's entity id; a bearer SubjectConfirmation whose `Recipient` is our address, `InResponseTo` our request and `NotOnOrAfter` not passed; Response `Destination` (when present) is our address; status Success; each assertion id works once (an in-memory record until it expires; with several servers the one-time cookie is what stops a replay).
- **XML is read safely:** DTDs prohibited, no resolver, a size limit of 400 KB.
- **Who the person is** is decided by the same code as OpenID Connect and LDAP (`ExternalIdentityResolver`): the provider's id (the NameID, with the entity id as issuer) first; the first time, the email (attribute, or a NameID of email format) of an existing account within the allowed domains; a disabled account is never switched on; an account tied to a different NameID is refused; unknown people get an account only with `AutoCreate` and `AllowedDomains` and only `DefaultRoles`. The provider is trusted for the email's correctness (an administrator configured it). Roles in the assertion are never read.
- **Endpoints:** `GET /api/auth/saml` (list), `GET /api/auth/saml/{provider}/login?next=`, `POST /api/auth/saml/{provider}/acs`, `GET /api/auth/saml/{provider}/metadata` (SP metadata for the provider's administrator). Errors go back to `/login?sso_error=<code>`. A session is made as for a password.

## Consequences
- Not yet: signed AuthnRequests, encrypted assertions, single logout, metadata import from a URL (certificates are pasted into the configuration), ECDSA signatures, replay memory shared between servers.
- Tested against a stand-in provider that signs with a generated certificate; not yet run against a real ADFS or Entra ID tenant.
