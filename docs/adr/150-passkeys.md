# ADR-150: Passkeys (WebAuthn) as a way to sign in

**Status:** accepted

## Context
Passwords are the weak point of every sign-in. Passkeys replace the password with a key pair held by the person's device and unlocked by a fingerprint, face or PIN; the browser binds each one to the site's domain, so a look-alike site gets nothing. The plan listed passkeys as the missing second kind of strong sign-in (after TOTP, ADR-039, and email codes, ADR-127).

## Decision
- **A passkey signs a person in by itself.** The server asks for *user verification*, so the device has already checked the person; a passkey sign-in therefore asks for no further code and is not subject to the password lockout (a signature cannot be guessed). A disabled account, or one without a usable password record, still cannot sign in. The password keeps working; passkeys are an addition, never a replacement the server forces.
- **Protocol written out on the platform, no library:** a small CBOR reader (`Cbor`), the authenticator-data layout, ES256 (ECDSA P-256) and RS256 (RSA 2048+) verification with `System.Security.Cryptography`. No attestation is requested (`attestation: none`) and none is verified: any authenticator is welcome, and what we rely on is the signature, not the maker of the device.
- **Strict checks on every ceremony:** a one-time challenge carried in a protected, 5-minute token that works once (replays are refused); the client data's `type`, `challenge` and `origin` (the origin must be one of ours, never cross-origin); the authenticator data's RP-ID hash, *user present* and (for sign-in) *user verified* flags; the signature over `authData ‖ SHA-256(clientData)`; and a **signature counter** that must move forward when the device keeps one (a counter that stands still or goes back is refused as a possible clone). For a key made on a device, the credential id in the attestation must equal the one reported, and the key must be a valid point on the curve. Every sign-in failure gives the same answer (401), so nothing tells an attacker which step failed.
- **Where passkeys belong:** the relying-party id and the allowed origins come from `Qahwa:Auth:Passkeys` (`RpId`, `Origins`); when empty, from the site's `Qahwa:Auth:PublicUrl`, and only as a last resort from the address the request arrived at. Each site of a multi-site server therefore has its own passkeys (they are rows of that site's database). A passkey registered for one domain never matches another, which is the browser's own protection.
- **Storage:** Core DocType `Passkey` (user, credential id, public key as SubjectPublicKeyInfo, algorithm, sign count, label, last used). Only System Managers can see or delete rows through the generic API; the public key is at permission level 9 like other secrets. A person has at most 10.
- **Registering needs the password again**, as turning on two-factor does: a stolen session must not be able to leave a permanent way back in. (People whose accounts come from LDAP have no local password and cannot register one yet.)
- **API:** `GET /api/auth/passkey` (is it on), `POST /api/auth/passkey/login/begin` and `/login` (rate limited with the login limit), and for the signed-in person `GET/POST /api/auth/passkeys`, `POST /api/auth/passkeys/begin`, `DELETE /api/auth/passkeys/{id}`. Desk: a **Sign in with a passkey** button on the login page (when the browser supports it and passkeys are on) and a **Passkeys** section on My account.
- `Qahwa:Auth:Passkeys:Enabled = false` turns it all off (the endpoints answer 404).

## Consequences
- Tested with a stand-in device (`FakeAuthenticator`) that makes real ES256 and RS256 keys and the same bytes a browser sends, against the real endpoints: registration and sign-in, wrong domain, wrong page, wrong challenge, not-verified, bad signature, someone else's user handle, unknown passkey, replayed answer, counter going back, duplicate device, removal by the owner only, and a disabled account.
- **Not exercised against a real browser or hardware key in this change** (the in-app browser cannot supply an authenticator); the Desk code uses the standard `navigator.credentials` calls and has unit tests for its conversions. Try it on a real device before relying on it, and keep passwords as a fallback.
- Not yet: asking for a passkey after the password as a second factor, an administrator resetting a person's passkeys (the person removes them, or an administrator deletes the rows), attestation checks for organisations that must allow only certain devices, security-key-only policies, LDAP accounts.
